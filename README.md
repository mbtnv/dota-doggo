# dota-doggo

Go-реализация Telegram-бота для отслеживания Dota 2.
Полезные сценарии исходного dota-dog сохраняются; архитектура и обработка ошибок
проектируются под Go. [План](docs/go-migration-plan.md) и
[функциональный контракт](docs/functional-contract.md) описывают объём работ.

Реализованы CLI `bot`/`worker`/`import-legacy`/`migrate`/`healthcheck`, принятие
существующей Python-базы, отчёты, HTML-форматирование, OpenDota и все команды
из функционального контракта. `/resync` загружает историю в фоне.
Worker опрашивает новые матчи, отправляет уведомления и автоотчёты.
Функциональность и Docker-запуск проверяются локально. Есть Compose для разработки
и проверки готовности процессов.
Первый запуск планируется на VPS с новой БД: старая установка недоступна.
Подготовлен автоматический деплой через GitHub Actions после успешных проверок
при push в `main`; реальный VPS ещё не подключён.

## Разработка

Требуются Go 1.26.5 и PostgreSQL 17. Версия Go закреплена в `.go-version` и `go.mod`.

```sh
go mod download
make check
make build
bin/dota-doggo --help
```

Приложение читает `.env`, при этом переменные процесса имеют приоритет.
Образец — `.env.example`. Для команд БД `BOT_TOKEN` не требуется.
Невалидные интервалы, timezone, proxy URL и идентификаторы пользователей
отклоняются до подключения к БД. Логи маскируют токены и credentials URL.

## Локальная тестовая база

```sh
docker compose -p dota-doggo-test -f compose.test.yml up -d --wait
export TEST_DATABASE_URL='postgres://postgres:local-test-only@localhost:55439/dota_doggo_test?sslmode=disable'
make test-integration
DATABASE_URL="$TEST_DATABASE_URL" bin/dota-doggo migrate
DATABASE_URL="$TEST_DATABASE_URL" bin/dota-doggo migrate status
DATABASE_URL="$TEST_DATABASE_URL" bin/dota-doggo healthcheck
docker compose -p dota-doggo-test -f compose.test.yml down -v
```

Integration-тесты создают случайные отдельные схемы и удаляют их по завершении.
Они не используют `.env`. Нужны права CREATE SCHEMA для тестового пользователя.
Unit-тесты работают без PostgreSQL, Python и сетевых API.
HTTP-клиенты и proxy проверяются локальными серверами `httptest`.
`healthcheck` проверяет соединение с PostgreSQL. `healthcheck bot|worker`
проверяет готовность работающего процесса через его loopback `HEALTH_ADDR`.

## Запуск бота

После настройки `.env` на отдельном тестовом токене и базе:

```sh
make build
bin/dota-doggo migrate
bin/dota-doggo bot
```

`bot` также проверяет и применяет миграции при старте, затем определяет своё
имя через `getMe`. Команды с `@имя_бота` адресуются только этому боту.
Для `/track` и `/resync` нужны права администратора или allowlist; остальные
правила описаны в функциональном контракте. Примеры:

```text
/track https://www.dotabuff.com/players/123456789 mid carry
/players
/resync 7 mid carry
/report week mid carry
/last 5 123456789
/status
```

При указании числового игрока в `/last` и `/resync` сначала передавайте число
матчей/дней: `/last 5 123456789`. Первый числовой аргумент трактуется как лимит.
Старую историю за пределами окна `recentMatches` загружает `/resync`.

Очередь resync хранится в памяти: один выполняющийся job, до 16 ожидающих,
без повторной постановки одного topic. При остановке активный запрос отменяется,
ожидающие задачи не запускаются; после перезапуска команду нужно повторить.
Задача ограничена 30 минутами. При истечении лимита отправляется частичный
итог через отдельный короткий context: сохранённые данные, ошибки и список
незавершённых игроков, включая ещё не начатых. При остановке процесса новые
сообщения не отправляются. Успешно сохранённые матчи остаются при частичных ошибках.
Курсор текущего topic сдвигается к максимальному успешно сохранённому ID;
последующий опрос worker не должен уведомлять об уже загруженной истории.

OpenDota использует отдельный HTTP transport, последовательные запросы,
отменяемое ожидание квоты и ограниченные повторы сетевых ошибок, 429 и 5xx.
Справочники обновляются в фоне; при сбое остаётся прежний кэш и встроенные
названия. Пропущенные метрики не затирают сохранённые значения, явные нули
обновляют их. Интерактивные команды ограничены минутой, запросы профиля
и лимитов — 30 секундами, поэтому ожидание квоты не занимает polling бесконечно.

Telegram поддерживает HTTP/HTTPS CONNECT, SOCKS5 и SOCKS4a с удалённым DNS.
SOCKS4 допускает username, но не пароль и не IPv6 literal адрес назначения.
Настройка `TELEGRAM_PROXY_URL` применяется только к Telegram.
HTTP/HTTPS и SOCKS5 выполняет стандартный transport Go, SOCKS4a — отдельный dialer.
HTML делится с сохранением тегов, сущностей и Unicode. Повтор не отправляет
заново уже успешные части в пределах одного вызова. Worker дополнительно
сохраняет стабильный текст и прогресс частей в PostgreSQL, возобновляя отправку
после ошибки или перезапуска. Неопределённый исход сетевой отправки/commit
всё ещё может приводить к дублям.

## Запуск worker

В отдельном процессе с тем же `.env` и PostgreSQL:

```sh
bin/dota-doggo worker
```

`bot` принимает команды, `worker` выполняет опрос и автоматические отправки;
оба процесса нужны для полной работы. Worker применяет/проверяет миграции
и проверяет токен через `getMe`. Первый цикл начинается сразу, следующий —
через `POLL_INTERVAL_MINUTES` после завершения предыдущего; циклы не перекрываются.

На одну PostgreSQL-базу допускается один worker: он удерживает отдельную
сессию с advisory lock. Нужен `DB_MAX_CONNS >= 2`, по умолчанию 5.
Сессия проверяется каждые 5 секунд и перед отправками; при потере блокировки
worker прекращает работу с ошибкой. SIGTERM отменяет запросы и ожидания,
после отмены новые циклы и отправки не начинаются.

Первый непустой опрос сохраняет матчи и устанавливает курсор без уведомлений.
Пустой ответ оставляет курсор неинициализированным. Дальнейшие уведомления
определяются курсором текущего topic, даже если общая история уже сохранена
другим topic. Неотправленные игры выбираются из сохранённой истории выше
курсора, даже если исчезли из окна recentMatches. Матчи отправляются по возрастанию ID; общий матч объединяет
известных отслеживаемых участников. Ошибка ответа одного игрока не мешает
остальным, но курсор проблемного игрока не сдвигается.

OpenDota запрашивается вне транзакций. Обновление истории и отправка каждой
части уведомления/автоотчёта используют короткие транзакции с блокировкой topic
и его текущих связей. Подтверждённая часть фиксируется отдельно; курсоры и
`report_runs` обновляются при завершении всей отправки. `/resync` использует ту же блокировку для каждого
сохраняемого матча; курсоры перечитываются после её получения.
Уже завершённый resync подавляет уведомления до своего курсора.
Ошибка отправки не сдвигает курсор, а ранее подтверждённые матчи остаются
подтверждёнными. Неопределённый исход отправки/commit может дать дубль.

Состояние опроса и безопасный текст ошибки видны в `/status`.
Запросы recentMatches, сохранение состояния и отправка одной части сообщения
ограничены минутой. `/status` показывает название/дату создания topic, интервал,
длительность/состояние опроса, нижнюю оценку следующего запуска и границы отчётов. Неудачные задачи повторяются в следующем цикле;
успешные topics и отчёты не откатываются из-за ошибок соседних.

Автоотчёты относятся к последнему завершённому day/week/month в таймзоне
topic, работают и во время паузы и записываются в `report_runs` после отправки.
Ручные отчёты не подавляют автоматические. Пустой день отмечается без сообщения;
week/month сохраняют отчёты с нулевыми игроками. Успешно отмеченный период
повторно не отправляется, в том числе после позднего backfill.
Ошибка загрузки откладывает формирование отчётов только затронутого topic.
Период сохраняется в БД и повторяется после успешного опроса, даже после
следующей календарной границы. Намеренная пауза не блокирует отчёты. Более старые
периоды, которые никогда не ставились в очередь, автоматически не рассылаются.

## Импорт старого players.json

Это отдельная операция для старого JSON; существующей Python/PostgreSQL-базе
достаточно принятия схемы через `migrate`.

```sh
bin/dota-doggo import-legacy --path players.json --chat-id -100123 --thread-id 42 --title "Dota"
bin/dota-doggo import-legacy --help
```

Без `--thread-id` импортируется основной чат. `BOT_TOKEN` не требуется;
таймзона берётся из `DEFAULT_TIMEZONE`. Формат файла:

```json
[{"id": "123456789", "name": "Example", "last_match_id": "999"}]
```

ID и курсоры принимаются как числа или десятичные строки без потери точности.
Весь файл проверяется до подключения к БД: корректные ID, непустые имена
до 255 символов, неотрицательные курсоры, отсутствие повторных игроков;
ограничение размера — 16 MiB. Импорт выполняется одной транзакцией.
Он добавляет отсутствующие связи, сохраняя существующие имена/profiles,
alias, настройки topic и курсоры. Повторный запуск возвращает ноль новых связей.
Игроки добавляются в порядке account ID. Новая связь получает legacy-курсор,
поэтому первый опрос после импорта уведомляет о матчах новее него.

## Существующая Python-база

До подключения Go проверить процедуру на копии базы. Команда `migrate`:

1. Проверяет наличие всех семи прикладных таблиц и `alembic_version`.
2. Требует Alembic revision `20260505_000004`.
3. Сверяет типы, nullable/default-поля, ключи, внешние связи и индексы
   с эталонной схемой в временной схеме внутри транзакции.
4. При соответствии записывает baseline 1 в `goose_db_version`, затем применяет
   миграцию 2 с таблицами `report_deliveries` и `match_deliveries`. Существующие
   записи, курсоры, ID и последовательности не меняются.

Создание временной схемы требует CREATE на базе. Дополнительные обычные индексы
разрешены; неизвестные определения колонок, ограничения и уникальные индексы
отклоняются до принятия baseline. Имена индексов и ограничений несущественны.
На пустой базе создаётся исходная схема вместе с Alembic marker, затем таблицы
доставки Go. Текущая версия схемы — 2. Старый Go-бинарник версии 1 откажется
запускаться с такой БД; для возврата требуется отдельное восстановление backup.
Миграции сериализованы advisory lock.
Повторный `migrate` повторяет проверку совместимости существующей схемы.
Команды удаления baseline нет: это защищает историю от случайного удаления.

Поддерживается нормализация старого `postgresql+asyncpg://` DSN в стандартный
`postgresql://`; менять существующий env только ради драйвера не обязательно.

## Проверки и контрольные данные

```sh
make check                    # gofmt, vet, unit tests с race detector
make test-integration         # PostgreSQL, миграции, репозитории, конкуренция
make build
make test-containers           # Docker + Python 3.9+, реальные bot/worker, fake API
make test-production-compose   # Также новая БД, перезапуск и backup/restore
make test-deploy               # Ошибки и откат сценария деплоя в Linux
```

CI выполняет те же проверки на отдельной PostgreSQL и в Docker. После успешных
проверок push в `main` публикует образ в GHCR и обновляет VPS по SSH. Нужна
однократная настройка сервера и GitHub variables/secrets; удалённый запуск
ещё не выполнялся. Инструкция — [deployment.md](docs/deployment.md).
Контейнерный сценарий не обращается к внешним API и удаляет только собственные
контейнеры, volumes и сеть; перехваченные сообщения — `.cache/container-smoke.json`.

`testdata/` содержит обезличенные примеры API, эталонные расчёты Python,
границы периодов и legacy-схему с тестовыми данными.
Эталонные тексты служат справочным материалом; побайтовое совпадение не требуется.

В `scripts/` остаются только инструменты деплоя и проверки текущей Go-версии:

- `deploy_vps.sh` — доставка релиза на VPS по SSH из GitHub Actions.
- `test_deploy.sh` — проверка ошибок, отката и SSH-сценария деплоя.
- `smoke_containers.py` — проверка bot/worker с тестовыми API в Docker.
- `smoke_production.py` — проверка VPS Compose, перезапуска и backup/restore.

Контейнерные проверки требуют Python 3.9+ со стандартной библиотекой;
исходная Python-версия бота для них не нужна.
